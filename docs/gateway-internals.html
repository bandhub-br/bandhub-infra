⚙️ 1. O que é YARP e como funciona o Gateway

O Gateway usa YARP (Yet Another Reverse Proxy), uma biblioteca da Microsoft que transforma uma ASP.NET Core app em um proxy reverso de alta performance. É o único ponto de entrada externo da sua arquitetura.

O que YARP faz por baixo dos panos

  • Recebe a requisição HTTP — o cliente (Postman, front-end, app mobile) envia a requisição para o Gateway.
  • Route Matching — YARP percorre a lista de rotas configuradas no appsettings.json e encontra a primeira que bate com o path da requisição usando pattern matching (ex: /bff/{**catch-all}).
  • Transforms — antes de encaminhar, YARP aplica as transformações configuradas. No seu caso, a rota bff-route remove o prefixo /bff via PathPattern: {"{**catch-all}"}.
  • Load Balancing / Destination Selection — YARP seleciona um destino do cluster (no seu caso, só há um destino por cluster). Em produção com múltiplas instâncias, ele distribui requisições automaticamente.
  • Proxy da requisição — YARP faz um HTTP forward para o serviço de destino copiando headers, body e método. Retorna a resposta ao cliente.

O Program.cs do Gateway (minimalista)

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddReverseProxy()                         // registra YARP no DI
    .LoadFromConfig(                             // carrega rotas do appsettings
        builder.Configuration.GetSection("ReverseProxy"));

var app = builder.Build();
app.MapReverseProxy();                          // registra o middleware do YARP
app.Run();

Isso é tudo. YARP abstrai o proxy inteiro. Nenhum controller, nenhuma lógica de negócio — apenas roteamento.

🗺️ 3. Como o roteamento e transforms funcionam

Rotas configuradas no Gateway

// appsettings.json → ReverseProxy → Routes

"auth-route":     { Path: "/auth/{**catch-all}"     } → AuthService  :5290  (sem transform)
"accounts-route": { Path: "/accounts/{**catch-all}" } → UserService  :5293  (sem transform)
"bands-route":    { Path: "/bands/{**catch-all}"    } → BandService  :5081  (sem transform)
"bff-route":      { Path: "/bff/{**catch-all}"      } → BFF          :5223  (remove prefixo /bff)

Por que a rota bff-route tem transform e as outras não?

As rotas diretas (auth-route, accounts-route, bands-route) preservam o path completo. O AuthService já expõe /auth/login, então chamar /auth/login no Gateway funciona sem transform.

Já o BFF expõe /accounts/login (sem prefixo). Se não houvesse o transform, o Gateway enviaria /bff/accounts/login para o BFF e daria 404, porque o BFF não conhece o prefixo /bff. O transform PathPattern: {"{**catch-all}"} captura tudo após /bff/ e usa como path final.

Como o {**catch-all} funciona

URL recebida no Gatewaycatch-all capturaURL enviada ao destino
/bff/accounts/loginaccounts/login/accounts/login
/bff/accounts/registeraccounts/register/accounts/register
/auth/loginlogin/auth/login (sem transform)

Como YARP substitui variáveis de ambiente (Docker)

O .NET lê configuração de múltiplas fontes em ordem de prioridade. Variáveis de ambiente sobrescrevem o appsettings.json usando __ como separador de seção:

# Equivalente a ReverseProxy.Clusters.bff-cluster.Destinations.destination1.Address
ReverseProxy__Clusters__bff-cluster__Destinations__destination1__Address=http://bandhub-bff:8080

🐳 4. Arquitetura Docker completa

Serviços criados

bandhub-gateway Gateway

Único ponto de entrada. Expõe a porta 5000 no host. YARP roteia para os outros serviços.

bandhub-bff BFF

Backend-for-Frontend. Orquestra chamadas a AuthService, UserService e BandService. Não exposto externamente.

bandhub-authservice Auth

Emite e valida JWT tokens. Rate limiting de 5 req/min no login. Banco: users_db.

bandhub-userservice Users

Gerencia contas de usuário. Banco: users_db (schema compartilhado com AuthService).

bandhub-bandservice Bands

Gerencia bandas. Banco: bands_db.

migrate-userservice Job

Roda dotnet-ef database update para users_db e encerra. Executa antes de authservice e userservice.

migrate-bandservice Job

Roda dotnet-ef database update para bands_db e encerra. Executa antes de bandservice.

🚀 5. Como subir tudo com Docker

Primeira vez (build das imagens + migrations)

# Navegue para a pasta da infra
cd BandHub/bandhub-infra/docker

# Build de todas as imagens e sobe tudo
docker compose up --build
Na primeira execução, o Docker vai:
1. Compilar todas as imagens .NET (pode demorar alguns minutos)
2. Subir o Postgres e aguardar o healthcheck
3. Rodar as migrations (migrate-userservice e migrate-bandservice) e encerrar os containers
4. Subir os serviços de aplicação e o Gateway

Próximas execuções (sem rebuild)

docker compose up -d

Parar tudo

docker compose down

Parar e remover volumes (reset completo do banco)

docker compose down -v

Ver logs de um serviço específico

# Logs do Gateway em tempo real
docker logs bandhub-gateway -f

# Logs do AuthService
docker logs bandhub-authservice -f

Rebuild de apenas um serviço

# Apenas rebuilda e reinicia o BFF
docker compose up --build bandhub-bff
Atenção: Os serviços .NET usam UseHttpsRedirection() no Program.cs. Dentro do Docker (HTTP only), isso é seguro — sem um listener HTTPS configurado, o middleware não redireciona. Os serviços se comunicam em HTTP puro dentro da rede Docker.
